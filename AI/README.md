# KAVACH Local AI Engine Documentation

**Architecture Principle**:  
*REAL SCANNER → RAW RESULT → EVIDENCE ENGINE → VALIDATED FINDING → OLLAMA → AI EXPLANATION → REMEDIATION → USER*

Ollama is **NOT** the vulnerability detector. Ollama is KAVACH's dedicated **Local AI Explanation Engine**. It never invents findings, CVEs, or terminal evidence.

---

## 1. What is Bundled vs. What Must Be Installed

| Component | Status in KAVACH USB / Executable | Description |
| :--- | :--- | :--- |
| **KAVACH Engine & UI** | **100% BUNDLED** | Standalone executable (`KAVACH.exe`) containing the FastAPI backend, React dashboard, SQLite database, offline CWE/OWASP knowledge bank, and rule-based deterministic fallback engine. |
| **Deterministic Fallback Engine** | **100% BUNDLED** | Ensures KAVACH functions with zero degradation if Ollama or the model is offline. |
| **Centralized AI Config** | **100% BUNDLED** | `AI/config.json` defining endpoint, model name, timeouts, and masking rules. |
| **Ollama Runtime** | **EXTERNAL INSTALLATION** | Must be installed on the host system or USB drive. Download from [https://ollama.com](https://ollama.com). *Ollama is NOT embedded inside KAVACH.exe to keep the binary lightweight (~55 MB).* |
| **LLM Model Weights** | **EXTERNAL DOWNLOAD** | Pinned model weights (e.g. `llama3`) must be pulled via `ollama pull llama3`. |

## 2. Hardware & Storage Requirements

- **Model Recommended**: `llama3:8b` (default) or `mistral:7b`, `phi3:mini` (for lower RAM devices).
- **RAM**: Minimum 8 GB (16 GB recommended for smooth concurrent LLM inference).
- **CPU / GPU**: Modern x86-64 CPU with AVX2 support; optional NVIDIA GPU with CUDA for sub-second responses.
- **Storage**:
  - KAVACH Executable & Dependencies: ~55 MB
  - Llama 3 8B Model: ~4.7 GB (stored in standard Ollama models directory)
  - Mistral 7B Model: ~4.1 GB
  - Phi-3 Mini (3.8B): ~2.2 GB

## 3. Ollama Automatic Startup Behavior

When `KAVACH.exe` launches:
1. **Step 1**: It queries `http://127.0.0.1:11434/api/tags` to check if Ollama is already active.
2. **Step 2**: If active, it inspects whether the configured model (`llama3`) is pulled and ready.
3. **Step 3**: If ready, it transitions the AI Status to 🟢 **`AI READY`**.
4. **Step 4**: If Ollama service is not running and `auto_start: true` is enabled in `AI/config.json`, KAVACH attempts to start the local Ollama service in the background:
   - Checks system `PATH` for `ollama`
   - Checks standard install path: `%LOCALAPPDATA%\Programs\Ollama\ollama.exe`
   - Spawns `ollama serve` with `OLLAMA_ORIGINS=*`
   - Sets AI Status to 🟡 **`AI STARTING`** while waiting for socket readiness.
5. **Step 5**: If Ollama is not installed or the model is unavailable:
   - Status switches honestly to 🟠 **`MODEL UNAVAILABLE`** or 🔴 **`AI OFFLINE`**.
   - **KAVACH NEVER BREAKS**. Scanners, evidence engine, risk prioritization, reports, and remediation guidance continue operating in 100% deterministic rule-based mode.

## 4. Sensitive Data Masking Guardrail

Before any finding context is forwarded to the local model, KAVACH sanitizes the payload:
- **AWS Keys** (`AKIA...`) are masked as `AKIA***[MASKED]`.
- **Database Passwords** (`postgresql://user:pass@host/db`) are sanitized to remove plaintext credentials.
- **Bearer Tokens / JWTs** have sensitive signature segments truncated and masked.
- **Private Key Blocks** (`BEGIN RSA PRIVATE KEY`) are completely redacted.
- Raw system dumps and unconsented directory paths are never sent to the model.

---

## 5. Standardized 7-Section Output Format

Every AI explanation generated by KAVACH follows strict structured sections:
1. `WHAT WAS FOUND`
2. `WHERE`
3. `WHY IT MATTERS`
4. `POSSIBLE IMPACT`
5. `RECOMMENDED ACTION`
6. `HOW TO FIX`
7. `HOW TO VERIFY`
